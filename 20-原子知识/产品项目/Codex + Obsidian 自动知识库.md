# Codex + Obsidian 自动知识库

标签：#codex #obsidian #knowledge-base #workflow #产品项目

## 核心内容

`Codex + Obsidian 自动知识库` 不是一个单一产品名，而是一类工作流样本：把 Obsidian 当知识库容器，把 Codex 当整理、问答、改写和执行层，让笔记系统从“静态仓库”变成“可操作的本地工作台”。

从目前能补到的原始来源看，这条路线至少已经有三种实现形态：把 Codex 直接嵌进 Obsidian 面板、把 Obsidian 通过 REST/MCP 暴露给 AI agent、以及用 Codex SDK 或插件体系把外部工作流接进知识库。

## 我的判断

这条线值得继续跟踪，因为它和你自己的 `knowledge-workspace-mcp` 主线高度重合。真正有价值的不是“把 AI 放进笔记软件”，而是把知识库变成 Agent 可读、可整理、可局部更新、但仍保留用户确认的工作台。

如果只把 Obsidian 当聊天上下文，这条路线价值有限；如果能把 `工作台 -> 输入流 -> 原子知识 -> 主题地图 -> 回写复盘` 串起来，它就会更像一个个人知识工作操作系统。

## 目前可见的三种路线

### 1. 把 Codex 放进 Obsidian

社区插件已经在做这件事。它们让 Codex 直接在 vault 里读取上下文、显示工具活动、提出文件改动并等待用户审核。

### 2. 把 Obsidian 暴露给 Agent

Obsidian 的本地 REST API / MCP 路线让外部 agent 安全读写 vault，适合把知识库当外部记忆和工作区，而不是把所有交互都塞进笔记软件本体。

### 3. 用 Codex 的插件 / SDK 把知识工作流程序化

Codex 已经支持插件和 SDK，这意味着知识库整理、回写、主题地图更新和任务续跑都可以逐步从“手工提示”升级为“可编排工作流”。

## 为什么它重要

- 它说明知识库开始从文档容器变成 Agent 工作介质。
- 它和 `私有 MCP 接入`、`Skill 资产化`、`session visibility` 是同一条大主线上的不同切面。
- 对你当前系统，它是外部对照样本，能帮助判断 `knowledge-workspace-mcp` 应该优先补什么，不该补什么。

## 当前边界

- 社媒收藏只是线索，不是正式证据。
- 目前补到的原始来源能证明“Codex 进 Obsidian”与“Obsidian 对 AI agent 开放接口”都已存在，但不能直接证明某个抖音条目展示的完整自动化方案已经成熟。
- 更稳的推进方式是把它当成 `工作流样本`，再逐步比较你的本地知识库动作缺少哪些能力。
