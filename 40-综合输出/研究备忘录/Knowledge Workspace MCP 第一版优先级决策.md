# Knowledge Workspace MCP 第一版优先级决策

日期：2026-07-13

## 问题

`knowledge-workspace-mcp` 第一版，应该优先解决“整理资料”，还是“推进想法”？

## 结论

第一版先把“整理资料”做稳，再逐步补“推进想法”。

这不是说“推进想法”不重要，而是当前阶段更需要先验证一个低风险、可复现、可确认的最小闭环：

```text
读取工作台 / 整理建议 -> 形成候选 -> 用户确认 -> 创建原子知识 -> 逐步更新主题地图
```

## 为什么先做整理资料

### 1. 输入输出更清楚

“整理资料”更容易定义：

- 读哪些文件。
- 产出什么草稿。
- 何时需要用户确认。
- 写入到哪个目录。

相比之下，“推进想法”更容易涉及优先级判断、长期方向选择、主题地图结构调整和跨多条笔记的综合决策。

### 2. 风险更低

第一版最怕的不是功能少，而是错误写入知识库。资料整理天然更接近“把已有输入整理成结构化草稿”，风险小于让 Agent 直接推动问题拆解、路线判断或长期规划。

### 3. 更适合验证 MCP 的受控写入边界

当前已实现的 `read_workbench`、`read_suggestions`、`create_atomic_note`，本质上都更贴近整理动作。先把这条链路做稳，才能知道：

- 读取范围是否合适。
- 草稿结构是否稳定。
- 用户确认点是否足够清楚。
- 写入后的知识是否真正可用。

### 4. “推进想法”依赖更高层能力

要让 MCP 真正推进想法，至少还需要更稳定的：

- 下一步建议生成。
- 主题地图更新。
- 判断形成路径可见化。
- 更明确的人工接管和回滚边界。

这更像第二版能力，而不是第一版就该强上。

## 当前阶段怎么理解“推进想法”

当前不应该让 MCP 直接替代思考，而应该让它先成为推进想法的辅助层：

- 帮你把待拆解问题收束成候选。
- 帮你把相关输入流和已有知识拉齐。
- 帮你生成可确认的原子知识草稿。
- 在确认后，再把结果回写到知识库。

也就是说，第一版先做“整理层”，第二版再补“建议层”和“地图更新层”。

## 对下一版实现顺序的影响

建议顺序：

1. 先补 `suggest_next_action`
2. 再补 `update_topic_map`
3. 之后再考虑更显式的 session 轨迹、判断路径和上下文压缩能力

原因是 `suggest_next_action` 可以先把“推进想法”做成建议，而不是直接写入；它的风险明显低于主题地图自动改写。

## 当前工作结论

- `knowledge-workspace-mcp` 的第一版目标，应该是“把整理动作做成稳定闭环”。
- “推进想法”暂时以候选推荐和草稿生成形式出现，不直接替代用户决策。
- 真正进入“推进想法”阶段的前提，是建议能力、地图更新能力和过程可见性足够稳定。
