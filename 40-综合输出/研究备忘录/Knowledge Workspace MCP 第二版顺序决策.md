# Knowledge Workspace MCP 第二版顺序决策

日期：2026-07-14

## 问题

`knowledge-workspace-mcp` 第二版，应该先补 `suggest_next_action`，还是先补 `update_topic_map`？

## 结论

第二版先补 `suggest_next_action`，再补 `update_topic_map`。

## 为什么先做 `suggest_next_action`

### 1. 它更接近“建议层”，风险低于直接改地图

`suggest_next_action` 的产出本质上还是候选、排序和建议动作。即使判断一般，也只是影响你下一步看什么，不会直接把主题地图写歪。

相比之下，`update_topic_map` 一旦做得过早，就会把尚未稳定的判断直接写进正式结构，污染面更大。

### 2. 它正好承接第一版整理闭环

第一版已经证明了这条链路成立：

```text
读取工作台 / 整理建议 -> 形成候选 -> 用户确认 -> 创建原子知识
```

第二版最自然的补强，不是直接自动改结构，而是让系统更稳定地回答：

- 当前最值得推进什么？
- 建议动作是什么？
- 需要先找哪些上下文？
- 哪条更适合创建原子知识，哪条更适合只保留为问题？

这正是 `suggest_next_action` 的职责。

### 3. 它能先把“推进想法”做成可见能力

你当前最缺的不是“自动写更多”，而是“把下一步判断说清楚”。`suggest_next_action` 能把 MCP 从整理工具，推进到轻量决策辅助层，但仍保留人工确认边界。

这也更符合当前知识库的工作方式：先让系统推荐，再由你确认是否升级为正式知识。

### 4. `update_topic_map` 依赖更成熟的判断稳定性

主题地图更新并不是简单加链接。它其实隐含了更高层判断：

- 这个概念是否已经足够稳定？
- 它应归到哪个主题分支？
- 是补“相关笔记”，还是改“当前判断”？
- 是新增长期变量，还是只是今天的热门样本？

如果没有更稳定的建议层和证据链，自动改图容易把短期噪音写成长期结构。

## `update_topic_map` 适合放在什么阶段

它更适合放在第二版后半段，或第二版稳定后的小第三步：

1. `suggest_next_action`
2. 原子知识确认与创建更稳定
3. 再补 `update_topic_map`

这样地图更新会更多基于“已经确认过的原子知识”，而不是直接基于输入流或草稿候选。

## 当前落地建议

- 第二版主功能先做：`suggest_next_action`
- 输出形式先保持保守：
  - 给出 1 到 3 条候选
  - 标记建议动作
  - 标记是否需要用户确认
  - 给出推荐理由
- `update_topic_map` 暂时继续人工触发或半自动触发

## 当前工作结论

- `suggest_next_action` 是第二版最合适的先手能力。
- `update_topic_map` 不应先于建议层成熟。
- 第二版的目标不是“自动写更多”，而是“更稳定地推荐下一步”。
